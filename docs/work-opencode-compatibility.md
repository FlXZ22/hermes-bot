# OpenCode compatibility in Hermes Work

The audit uses the archived OpenCode repository supplied for this project, the maintained OpenCode 2.4.1 source, and Hermes Agent 0.21.0. Both OpenCode checkouts live under the Git-ignored `.upstream/` directory. The maintained checkout supplies the current Work feature reference. [Original OpenCode checkout](https://github.com/opencode-ai/opencode/tree/73ee493), [Maintained OpenCode checkout](https://github.com/anomalyco/opencode/tree/f25b090), [Hermes Agent checkout](https://github.com/NousResearch/hermes-agent/tree/29112bef09)

## Coding workflows

| OpenCode feature | Hermes support | Work integration |
| --- | --- | --- |
| Workspaces and project sessions | Workspace directory, persistent history, profile-scoped backend | Work and Chat lists and selections per profile. Each Work session binds to a workspace. |
| Read, search, edit, write, and apply patches | Native filesystem tools | Available to Hermes while working in the chosen project. |
| Shell, test runs, and code execution | Native terminal and code execution tools | Hermes runs commands in context. Desktop also provides workspace terminal tabs. |
| Build, Plan, and Explore | Native coding loop, `/plan`, and `llm.oneshot` | Work implements coding and planning. `/explore` uses the stateless, tool-free endpoint and sends only a bounded top-level listing or explicitly referenced workspace file excerpts. Autonomous discovery and a persistent Explore agent are not implemented. |
| Goals, tasks, and live steering | Native `/goal`, Todos, Kanban, queue, and steering | Work exposes goals, pause and resume, queued prompts, and steering. |
| Subagents, background jobs, and inter-session delegation | Native delegation and Kanban workers with different lifecycle APIs | Work displays running subagents and supports steering and cancellation. OpenCode background sessions, recovery, and cross-session job controls need further integration. |
| Clarifying questions and tool approvals | Native clarification and approval events; `tools.configure` updates profile configuration, not a single Work session | Work presents choices and tool approval controls. OpenCode path globs, per-agent tools, policy rules, and approval patterns require mapping plus session-scoped gateway enforcement. Explore does not change profile tool configuration. |
| Context compaction and context usage | Native compression, usage reporting, and session summary | Work supports `/compress`, usage and context commands, and preserves section placement through compaction. OpenCode compaction modes and provider-specific configuration differ. |
| File and image attachments, `@` references | Native attachments and context expansion for files, folders, Git state, and URLs | Work supports selecting contextual references and adding attachments. OpenCode reference aliases, external Git caches, and attachment preprocessing need adapters. |
| Git diff, review, staging, commits, branches, worktrees, and pull requests | Native Git dashboard endpoints and shell tools | Work supports per-file diffs, stage and unstage, commit, push, branch switching, worktree creation, and pull requests via GitHub CLI. The remote commit action uses the Hermes API’s staging behavior. Desktop Git can compare tracked changes against the state at the start of a turn. |
| Snapshots, undo, and redo | Hermes checkpoints, rewind, and rollback | Work previews and restores Hermes checkpoints and can rewind the prompt. OpenCode-style redo and full turn-based snapshots need further integration. |
| Session list, search, fork, archive, import, and export | Hermes session API and gateway | Work uses Hermes session actions and exports JSON. It imports conversation text from OpenCode v1 and v2 and Hermes Work exports. Tool replay, attachments, and OpenCode metadata require a richer migration format. |
| Custom slash commands | Native Hermes aliases and skills; OpenCode JSON and Markdown need a parser | Work exposes `/oc` and `/oc/<name>` for workspace command templates, arguments, and nested Markdown commands. Shell context is collected using Hermes tools. OpenCode model and agent routing, global commands, and configuration inheritance need further mapping. |
| Project instructions, skills, and custom agents | Hermes supports project instructions, skills, profiles, and subagents | `/init` and Hermes skills are available. Importing OpenCode agent definitions and every OpenCode instruction/skill discovery path needs an adapter. |
| Language servers, symbol navigation, and automatic formatters | Hermes LSP provides post-edit diagnostics. Shell tools can run project formatters. | A symbol navigator, diagnostic panel, and configured on-save formatters need Work integration. |
| Web search, web fetch, browser, image generation | Hermes offers profile-dependent search, browser, and image tools | Hermes makes enabled tools available during Work. Tool-specific interfaces and provider routing depend on the profile and configured integrations. |
| Models, providers, reasoning variants, and model warming | Hermes supports its own providers, model settings, and reasoning controls | Work uses the Hermes model picker and reasoning settings. OpenCode provider configuration, credential stores, and warming options need separate mappings. |
| MCP servers, plugins, and custom tools | Hermes supports MCP servers plus its own plugin and tool APIs | Profile-configured MCP and Hermes tools work in coding sessions. OpenCode MCP config needs translation. OpenCode server, GUI, and CLI plugins target a different runtime. |

## Desktop and ecosystem features

| OpenCode feature | Hermes support | Work integration |
| --- | --- | --- |
| Desktop project switcher, file tree, editor tabs, line comments, preview tabs, and navigation | Hermes has file, project, terminal, and Git APIs | Work has project navigation and file and Git panes. Editor tabs, line comments, expanded search/navigation, and preview workflows need more UI. |
| Command palette, shortcuts, themes, and terminal UI options | Hermes and this app each have their own controls and themes | The app has a command palette and shortcuts. OpenCode key maps, terminal workflows, and theme file formats need adaptation. |
| Voice, notifications, and session sharing | Hermes supports separately configured voice, messaging, and notifications | OpenCode desktop voice, notifications, and publicly shared sessions need separate Work UI and service integration. |
| Remote workspaces, server connection, and authentication | Native Hermes dashboard, authentication, and remote terminal configurations | Work can connect to a Hermes dashboard. OpenCode server discovery and OpenCode workspace connectors use different protocols. |
| CLI automation, headless jobs, SDK, and IDE protocol | Hermes exposes its own CLI, dashboard API, gateway, and automation | Work uses the Hermes API. OpenCode CLI flags, ACP, HTTP/SDK clients, and plugin contracts require adapters for compatibility. |
| Enterprise policy, organization, billing, and hosted Console | Hermes has its own authentication, profile configuration, and usage data | Work uses the configured Hermes instance. Organization, billing, SSO/SCIM, and hosted OpenCode integrations remain upstream services. |
